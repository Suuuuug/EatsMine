# 1등 전략 — EatsMine

작성: 2026-11-23. 근거: 대회 대시보드·신청 안내 직접 확인(docs/CONTEST.md 상단), 상위 3개 서비스 공개 페이지·sitemap 확인. 수치는 11-22 누적 잠정치이고 매일 바뀐다. **목표 수치는 추정이며 측정값이 아니다.**

## 결론

- 1등은 "좋은 서비스"가 아니라 **등록 이후 12-13까지 잇플로 보낸 순 사용자 수**로만 정해진다(심사 없음, 동점이면 먼저 등록한 팀).
- 현재 1위는 9,039명, 2위 1,325명, 3위 227명이다. **3위권은 수백 명이면 들어가고, 1위는 1만 명대 중후반이 필요할 가능성이 크다**(1위가 계속 늘고 있으므로).
- 상위 2팀의 공통점은 **고유 URL 페이지 수천 개**(sitemap 기준)와 **사람들이 원래 찾던 강한 소재**다. 단 sitemap 수는 색인·검색 유입의 증거가 아니고, 기존 독자·커뮤니티 게시·운영 기간 차이도 통제하지 못했다. 검색이 그들의 주 유입원이라는 것은 **가설**이다.
- 그래서 순서는: ① 최소 P0를 빨리 띄워 **등록 제출 → 등록 완료 회신**(집계 시작) → ② 색인을 기다리지 않는 **직접 배포 채널**(지역 커뮤니티·동아리·지역 콘텐츠 제작자와 허가받은 협업)을 주력으로 → ③ 소수의 유용한 지역 랜딩으로 SEO를 **제한된 실험**으로 → ④ 매일 대시보드로 확인하고 조정. 영토 공유 루프는 전환 의도가 낮을 수 있어 실험으로 둔다.

## 집계 규칙에서 나오는 필수 조건

1. **등록이 늦으면 그만큼 잃는다.** 집계는 **제출일이 아니라 검토 후 등록 완료일**부터다. 처리 기간과 보완 요청 가능성이 있으니 서명 서류·서비스 적격성·승인된 API 경로를 병렬로 준비한다. 기획서 일정(11.29~12.02 신청)은 늦다. **11-26 전후 제출**을 목표로 당기고, 홍보 확대는 등록 완료 회신과 정상 동작 확인 뒤에 한다.
2. **상세 링크는 브라우저에서 원본 그대로.** `eatpl-integration` 스킬 규칙. 단 하나의 예외도 실적 0으로 이어진다.
3. **인앱 브라우저는 유입이 유실될 수 있다.** 기획서 §15 홍보 채널(인스타그램, 카카오톡 공유, 에브리타임 앱)은 대부분 인앱 브라우저로 열린다. 그대로 두면 가장 큰 유입원이 집계에서 빠질 수 있다.
   - 대응 가설: 인앱 브라우저(UA에 `KAKAOTALK`, `Instagram`, `FBAN/FBAV`, `NAVER(inapp`, `Line`, `everytime` 등)를 감지하면, **잇플 URL이 아니라 등록 호스트의 EatsMine 페이지(현재 검색 상태 포함)를 외부 브라우저에서 다시 열도록** 안내하고, 사용자가 거기서 원본 merUrl을 누르게 한다. 잇플 URL을 바로 외부로 넘기면 등록 도메인 경유 증거가 사라질 수 있다. 외부 열기 스킴(카카오톡, 안드로이드 intent 등)의 동작과 집계 반영은 **미검증**이다. 안내 적용 전후의 이탈률과 공식 순 사용자 증가를 비교해 채택을 정한다.
   - 안내가 강제 팝업처럼 보이면 기획서 원칙(이동 직전 팝업 금지)과 충돌한다. 인앱일 때만, 이동 버튼 근처에서 한 번만 보여준다.
4. **체류 요건이 있다.** 기준은 미공개. 잇플 상세에서 실제로 볼 이유가 있는 사용자(그 지역에서 지금 먹을 곳을 찾는 사람)를 보내야 한다. 클릭 유도 문구로 아무나 보내면 집계되지 않는다.
5. **등록 호스트와 실제 유입 호스트가 같아야 한다.** `www`/루트, 프리뷰 도메인 혼용 금지. 12-03 전 1회 변경·전후 합산은 공식 문구지만, 변경 접수 방법·효력 시점·이전 호스트에서 계속 들어오는 유입 처리는 미확인이고 검색 재처리 시간도 든다. **가능하면 처음 등록한 호스트를 종료일까지 유지**한다. 바꿔야 하면 조건을 먼저 문의하고 canonical·공유 URL·등록 호스트를 함께 전환한다.

## EatsMine 전략

### 1. 속도: 최소 P0로 먼저 등록 (11-24 ~ 11-26)

- 범위: 지역 선택 → 잇플 결과 카드 → 원본 merUrl 이동. 지도(P0-03)는 등록 후 붙여도 될 가능성이 높다(공식 연결 요건은 "스킬 호출 + 상세 주소 연결"). 그러나 신청 안내가 "개발자가 만든 AI 서비스"라고 쓰고 비AI 서비스 적격성은 미확인이므로, **최소 AI 의도 분류(P0-05)를 포함하거나 주최 측에 먼저 문의**한다.
- 등록 도메인을 이 시점에 확정하고, 이후 모든 공유·검색 유입이 그 호스트로 들어오게 한다.
- 신청서 서명·제출은 사용자가 직접 한다.

### 2. 직접 배포 채널 (주력, 등록 완료 직후)

색인을 기다리지 않는 경로다. 한 지역을 골라 그 지역의 실제 식사 수요에 맞는 랜딩(예: "성균관대 자과캠 주변 결제 상위 맛집", "11월 제철 ○○")을 만들고, 그 지역 커뮤니티 운영자·대학 동아리·지역 콘텐츠 제작자와 **허가받은 협업**으로 배포한다. 신규 고유 사용자 확보량과 공식 인정 실적을 본 뒤 다른 지역으로 넓힌다. 보상성 클릭·무단 대량 발송은 하지 않는다.

### 3. 지역 × 음식 랜딩 페이지 (SEO, 제한된 실험)

1·2위의 구조를 참고하되 효과는 검증되지 않았다(위 "읽을 수 있는 것"). 소수의 유용한 페이지부터 노출·클릭·전환을 보고 늘린다. 종료일까지 색인이 안 돼도 계획이 무너지지 않게 2번이 주력이다. EatsMine 소재에 맞게:

- `/{시도}/{시군구}`(약 250개), `/{시군구}/{음식·업종}`, `/제철/{월}/{음식}`, `/역/{역명}` 같은 고유 URL. 기획서 §15 SEO 항목과 P1-05 테마 랜딩을 앞당기는 것이다.
- **얇은 자동 생성 페이지는 안 된다**(기획서 §15, 검색엔진도 걸러낸다). 페이지마다 실제 정보가 있어야 한다:
  - 요청 시점에 잇플 API로 그 지역·업종 매장을 조회해 보여준다. 약관상 원본 축적 금지이고 짧은 캐시 허용 여부도 미확인이므로, 확인 전에는 캐시 없이 요청 시점 조회만 한다(`eatpl-integration` 스킬).
  - 우리가 만든 고유 콘텐츠: 제철 식재료(KAMIS 시세, 절기 — `kamis-food-price`, `korean-holiday-calendar` 스킬), 그 지역 대표 음식 설명과 출처, 팀이 직접 확인한 한 줄 소개.
- 기술: 페이지별 `title`·`description`·OG 이미지, `sitemap.xml`, `robots.txt`, 구조화 데이터, 빠른 첫 화면. **네이버 서치어드바이저와 구글 서치 콘솔에 등록 즉시 sitemap 제출**(색인까지 며칠~수주 걸릴 수 있어 가장 먼저 해야 한다. 기간 안에 색인될지는 불확실).
- 카드의 잇플 CTA는 스크롤 없이 보이게. 페이지 하나당 이동률이 곧 실적이다.

### 4. 공유 루프: "내가 먹어본 지도 몇 칸?" (실험, P1-02·P1-04 일부)

- 지도 색칠에 관심 있는 사람과 지금 식당 상세를 볼 사람은 다를 수 있다. 공유 → 신규 인정 사용자 전환을 작은 실험으로 확인한 뒤 키운다.

- 1위의 소재처럼 **사람들이 스스로 퍼뜨릴 이유**가 필요하다. EatsMine의 차별점은 지역 영토 칠하기다. 로그인 없이 로컬 저장으로 칠하고, 결과 이미지 + "너도 칠하기" 딥링크를 공유한다.
- 공유받은 사람은 대부분 인앱 브라우저로 들어온다. 위 3번 인앱 대응이 없으면 이 루프의 실적이 사라질 수 있다. **인앱 대응을 공유 기능보다 먼저** 만든다.
- 공유 랜딩은 그 친구의 지역·음식 쿼리를 복원해 바로 잇플 카드까지 보여준다(기획서 §15).

### 5. 채널 (팀이 직접 실행, 사용자 승인 후)

- 에브리타임·학교 커뮤니티(홍보 규칙 확인), 인스타그램 스토리·릴스, 카카오톡 단톡, 지역 맛집 관련 커뮤니티, 개발기 SNS.
- 콘텐츠는 "11월 제철음식 도감", "○○구 결제 상위 맛집" 같이 **그 자체로 쓸모 있는 것**. 결과 페이지 링크는 등록 호스트로.
- 유료 광고는 순 사용자당 10원이라 리워드로는 회수되지 않는다. 1~3위 상금을 노린 투자로만 의미가 있고, 비용이 생기므로 사용자 승인 없이 하지 않는다.

### 6. 측정과 조정 (매일)

- 매일 14시 이후 대시보드에서 우리 순 사용자와 1~3위 수치를 기록한다(daily-log). 1위 증가 속도를 2~3일 관측해 필요한 목표를 다시 잡는다.
- "총 클릭 대비 순 사용자" 비율로 누락을 진단하지 않는다. 공식 집계는 기간 전체에서 같은 사람을 한 번만 세므로 재방문·반복 클릭이 늘면 정상이어도 비율이 떨어진다. 대신 **같은 기간의 신규 고유 아웃바운드 사용자(익명 세션 기준)**와 **공식 순 사용자 일일 증가량**을 비교하고, 반복 클릭·테스트·등록 완료 전 이벤트를 분리한다. 차이가 크면 인앱·체류·호스트 문제를 의심한다.
- 채널별 랜딩 URL을 다르게 써서(추적 파라미터는 **우리 페이지 URL에만**, 잇플 링크에는 절대 붙이지 않음) 어느 채널이 실제로 잇플까지 가는지 본다.

## 하지 않는 것

- 봇·자동화 클릭, 지인에게 반복 클릭 요청, 보상을 걸고 클릭시키기, 숨은 리다이렉트, 잇플 링크를 자동으로 여는 페이지. 집계 제외 사유이자 약관 위반 소지가 있고, 비정상 호출은 이용 제한 사유다.
- 잇플 데이터를 DB에 쌓아 페이지를 만드는 것(약관 제9조의2). 요청 시점 조회로만 쓴다.
- 1위를 흉내 낸 유명인 콘텐츠 복제. 우리 소재(제철·지역·영토)로 간다.

## 목표 (가설, 매일 갱신)

목표는 경쟁자 수치가 아니라 **필요한 유입량**으로 역산한다.

```text
필요 신규 방문 = 목표 인정 사용자 ÷ (방문→고유 아웃바운드 비율 × 아웃바운드→인정 비율)
예: 15,000명 ÷ (0.4 × 0.5) = 75,000 신규 방문  ← 계산 예시, 측정값 아님
```

등록 완료 후 첫 2~3일의 실측 비율로 이 식을 다시 채우고, 1위의 일일 증가량을 낙관·기본·비관 세 시나리오로 잡아 남은 집계일에 필요한 일일 확보량을 채널별 담당자·실행일과 함께 적는다.

| 시점 | 목표 | 근거 |
|---|---|---|
| 11-26 | 최소판 배포 + 신청 제출 | 집계는 등록 **완료**일부터, 회신 기간 미확인 |
| 11-30 | 누적 300명 이상 | 현재 3위 227명 |
| 12-06 | 누적 1,500명 이상 | 현재 2위 1,325명 |
| 12-13 | 1위 수치 초과 | 1위 증가 속도 관측 후 재설정. 현 추세면 1만 명대 중후반 추정 |

## 기획서와의 충돌 (팀 논의 필요)

- 기획서 §16 일정은 신청을 11.29~12.02에 둔다 → **11-26 전후로 당기자고 제안**.
- 기획서 §15 홍보 채널은 인앱 브라우저 위주다 → **인앱 대응을 P0 수준으로 올리자고 제안**.
- 기획서 P1-05 테마 랜딩·§15 SEO는 P0 이후다 → **지역 랜딩을 등록 직후 최우선으로 올리자고 제안**.
