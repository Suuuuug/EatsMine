# 잇플 챌린지 공고·전략 검토

## 먼저 읽을 것

1. `docs/CONTEST.md` 상단 "2026-11-23 재확인: EatsMine 참가 절차". 신청 순서, 일정, 집계 제외 사유, 보상, 미확인 항목.
2. `docs/WINNING-STRATEGY.md`. 순위 판세, 상위 서비스 분석, EatsMine 전략과 목표, 기획서와의 충돌 제안.
3. `docs/BLOCKERS.md`, 필요하면 `docs/CONTEST-REVIEW-2026-11-13.md`(약관 조항별 근거).

이 문서들은 확인 시점이 박힌 스냅숏이다. 판단이 걸린 사실(마감·집계 조건·순위)은 [공고](https://edu.bccard.ai/contest), [신청 안내](https://edu.bccard.ai/static/contest/apply.html), [신청서 PDF](https://edu.bccard.ai/static/contest/eatpl_challenge_application_form.pdf) 원문에서 다시 확인하고, 바뀌었으면 CONTEST.md에 날짜와 함께 기록한다. 캡처는 `research/contest-evidence/`.

## 핵심 규칙 (2026-11-23 기준)

- 순위는 심사 없이 **등록 이후 순 사용자 수**로만 정해진다. 동점이면 먼저 등록한 팀. 등록 완료일부터 집계되고, 동작하는 서비스가 있어야 등록된다. 그래서 등록을 앞당기는 작업이 대부분의 기능보다 먼저다.
- 잇플 상세 주소(`https://web.paybooc.ai/mer/web/profile/<id>`)를 받은 그대로 사용자 브라우저에서 연다. 서버 호출, 추적 파라미터, 단축·중간 페이지, 리다이렉트, **인앱 브라우저 유실**, 체류 미달, 호스트 불일치는 집계되지 않는다. 구현 규칙은 `eatpl-integration`.
- 클릭·페이지뷰는 순 사용자가 아니다. 자체 로그와 대시보드(매일 14시 갱신, 잠정치)를 따로 기록하고 비율을 본다.
- 1인 1서비스, 최대 4인. 도메인은 12-03 전 1회 변경, 전후 합산.

## 판단할 때

- 공식 문서의 사실, 사용자 목표, 추론, 미확인을 구분한다. 직접 열지 못한 폼·인증 영역은 확인했다고 쓰지 않는다. 상위 서비스의 트래픽 출처처럼 외부에서 볼 수 없는 것은 추론이라고 표시한다.
- 목표 수치는 가설로 쓰고 측정값과 섞지 않는다. 대시보드를 다시 봤으면 WINNING-STRATEGY.md의 판세 표와 목표를 갱신한다.
- 순위를 올리는 방법은 실제 사용자에게 쓸모 있는 유입(검색 랜딩, 공유, 커뮤니티 콘텐츠)만 제안한다. 봇·반복 클릭 요청·보상 걸린 클릭·숨은 리다이렉트·자동 이동은 제안하지 않는다. 비용이 드는 광고는 사용자 승인 사항으로만 제시한다.
- 전략이 기획서와 충돌하면 기획서를 조용히 바꾸지 않는다. 충돌과 제안을 WINNING-STRATEGY.md에 남기고 사용자에게 알린다.

## 하지 않는 것

신청서 작성·서명·폼 제출·문의 메일 발송·계좌/주민번호 처리는 사용자가 직접 한다. 서명본·개인정보·인증 화면을 저장소나 로그에 남기지 않는다. 변경 사항은 daily-log와 HANDOFF에 반영한다.
