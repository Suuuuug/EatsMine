# EatsMine UI 적용 규칙

정본은 `docs/DESIGN.md`다. 이 스킬은 "실제 화면에 어떻게 적용하나"를 다룬다. 판단 순서: 사용자 지시 > 팀 토큰·공통 컴포넌트 > DESIGN 금지 목록 > 아래 출처의 규칙 > 취향.

## 요청이 금지 목록과 부딪힐 때

사용자가 DESIGN.md §1 항목(통계 숫자 카드 띠, 영어 ALL-CAPS 라벨, 상태 배지, 왼쪽 굵은 띠, 회색 부연 등)을 콕 집어 요청하면, 반쯤 따르는 절충안을 만들지 않는다. 일관되게 이렇게 한다.
1. 같은 목적을 이루는 **대안을 먼저 만든다**(숫자는 기준과 함께 행이나 문장으로, 배지는 스위치와 글자로).
2. 답변 첫머리에 무엇을 바꿨는지와 근거(§1의 어느 항목, 사용자가 이전에 싫다고 한 것)를 한두 줄로 쓴다.
3. "원래 말한 모양으로 바꿀까요?"를 한 줄로 묻는다. 사용자가 그래도 원하면 그대로 따른다(판단 순서상 사용자 지시가 이긴다).

## 0. 만들기 전에 (클릭을 먼저 상상한다)

코드를 쓰기 전에 작업 계약(`docs/plans/active/<화면>.md`)에 적는다.
1. 이 화면의 **한 가지 일**은 무엇인가. 첫 화면 390px에서 그 일이 보이는가.
2. 사용자가 **처음 누를 곳**과 그 다음 두 번의 클릭. 엄지가 닿는 아래쪽에 있는가.
3. 각 클릭 뒤 화면이 어떻게 바뀌는가(어디가 바뀌고, 포커스는 어디로 가고, 되돌릴 수 있는가).
4. 빈 상태, 로딩, 오류, 예시 데이터 상태에서 각각 무엇이 보이는가.
5. 이 화면에서 **지울 수 있는 것**은 무엇인가(diagram-design: "The highest-quality move is usually deletion").

## 1. 페이지 UI (jungrok5/ai-design `polish-ui`, MIT)

- 섹션마다 같은 틀(아이콘+제목+설명)을 찍지 않는다. 세 섹션이 같은 모양이면 하나를 바꾼다.
- 히어로 아래 통계 숫자 띠를 두지 않는다. 숫자는 문장 안에서 기준과 함께("17곳 중 4곳").
- 패널을 중첩하지 않는다. 그룹은 1px 선이나 면 한 단계 차이로 나눈다.
- 설명이 필요 없는 항목은 제목으로 만들지 않는다. 짧은 이름-값 쌍은 `<dl>`.
- 색은 상태를 뜻할 때만. 색만으로 상태를 구분하지 않는다(글자·체크를 같이).
- 굵은 강조는 페이지당 한 곳(Spend boldness in one place).
- 주 버튼은 화면당 하나. 나머지는 `variant="muted"`나 글자 버튼.

## 2. 시각화: 영토 지도·도감 격자 (cathrynlavery/diagram-design, MIT)

- 모든 칸을 똑같이 그리면 위계가 사라진다. 초점은 1~2곳(지금 고른 지역, 가장 많이 칠한 곳)만 강조색.
- 그림자 대신 1px 선. 칸 모서리는 작게(6~10px).
- 한글 라벨 최소 12px. 안 들어가면 글자를 줄이지 말고 이름을 줄인다(서울특별시 → 서울).
- 칸 크기는 4px 격자에 맞춘다. 고정폭 글꼴은 숫자·코드에만.
- 시각화는 같은 정보를 담은 글자 목록과 함께 둔다(기획서 §8 접근성: 지도와 같은 정보의 텍스트 목록).

## 3. 마이페이지 구조 (토스·당근 관행, 일부 미검증)

- 위: 프로필 한 줄(이름, 핵심 수치 하나). 큰 환영 문구 금지.
- 가운데: 내가 한 것(칠한 지역, 모은 음식, 남긴 후기). 숫자는 눌러서 목록으로 가는 행.
- 아래: 설정(공개 범위). 행 오른쪽 스위치, 현재 상태가 보인다.
- 섹션 사이는 여백이나 면 차이로. 각 섹션을 유리 카드로 감싸지 않는다.
- 빈 상태: 이유 + 첫 행동 하나(앱인토스 가이드).
- 출처: [토스 단순함](https://toss.im/tossfeed/article/importance-simplicity), [앱인토스 화면 가이드](https://toss.im/apps-in-toss/blog/mini-app-ux-screen-design-guide). 당근 SEED·앱별 마이탭은 원문 미확인(일반 관행).

## 4. 토큰과 재질 (2026-11-24 갱신)

- 토큰은 `apps/web/src/styles/tokens.css` 하나에서 온다. 화면 파일에 hex·oklch를 쓰지 않는다.
- 사용자 지시(2026-11-24): iOS·macOS 기반 웹, 바탕 한 겹 빛번짐 그라데이션 + 글래스모피즘. 유리는 떠 있는 층(사이드바 `material-sidebar`, 상단·하단 바 `glass-bar`, 시트·토스트 `material-thick`, 그림 위 캡션)에만. 내용 면은 `surface`. 유리 위 유리, 장식용 유리 조각·블롭, 글자·버튼 그라데이션 금지(HIG Materials).
- `SectionTitle`(꺾쇠 장식)은 도구 화면에 쓰지 않는다. `StarRating`은 사용자 리뷰에만.
- `ItemCard`처럼 이미지가 전제인 컴포넌트에 가짜 이미지 자리를 넣지 않는다. 키트 그림(`public/images/foods` 등)이 있으면 그것을, 없으면 행 목록으로.
- 모바일 이동은 하단 유리 탭 바(1차) + 상단 칩 줄(2차), 햄버거 없음. 1024px 이상은 왼쪽 사이드바(DESIGN §8).

## 4-1. 부품 재사용 (토스 TDS·당근 SEED 방식)

- 앱 화면은 `@/components/em` 부품(ActionButton, IconButton, TextField, SearchField, Switch, Checkbox, SegmentedControl, FilterChip, ProgressBar, useToast, BottomSheet, Skeleton, EmptyState, FoodTile, AchievementBadge, SeasonBanner, MapMarker, TerritoryMap)과 `components/list/List.tsx`를 먼저 쓴다. 팀 `@/components/ui`는 팀 소개·마케팅 화면용.
- 화면 파일에 hover·active·focus 클래스, 행 높이, 구분선을 직접 쓰지 않는다. `pressable`, `focus-ring`, `field`, `list-row`, `list-group`/`list-divided` 유틸리티를 쓴다.
- 같은 모양이 두 화면에 나오면 부품으로 올리고 `docs/DESIGN.md` §7과 `/styleguide`에 같이 적는다.
- 새 그림이 필요하면 DESIGN §10 절차(Codex로 키트 화풍 제작 → 렌더 비교)를 따른다.

## 5. 끝내기 전 자가 점검 (그다음 ui-review-loop)

- [ ] 회색 부연 글자가 헷갈리는 곳 한 군데 이하
- [ ] 장식용 칩 0개, 한쪽 굵은 테두리 0개, 이모지 0개, eyebrow·ALL-CAPS 0개
- [ ] 강조색은 주 행동·현재 선택·채움 진행에만
- [ ] 390px에서 가로 스크롤 없음, 주 행동이 엄지 영역 안
- [ ] 모든 조작 44px, `focus-visible`, 선택 상태에 `aria-*`
- [ ] 빈·로딩·오류·예시 상태가 다 있다
- [ ] 예시 데이터는 예시라고 밝혔다
- [ ] 유리는 떠 있는 층에만, 내용 면은 surface(HIG Materials)
- [ ] fill 버튼 화면당 하나, 버튼 세 개 이상 나란히 없음, 파괴적 동작은 danger이고 주 버튼 아님(HIG·SEED)
- [ ] 세그먼트는 조작용 화면당 하나, 이동은 탭 바·칩 줄(SEED Tabs vs Segmented)
- [ ] 스위치는 즉시 반영, 나중 저장은 체크박스. 토스트는 4초·하나씩
- [ ] 투명도 줄이기·대비 높이기·동작 줄이기에서 읽힌다


## 6. 탐색 예시 확인 (2026-11-24)

- 지도·도감·마이 예시에서는 화면별 목적과 배경을 구분하고, PC에서 식당 목록과 지도가 함께 보일 공간을 먼저 확인한다.
- 전국→시도→상세 지역 흐름, 리뷰 유무에 따른 도감의 흑백·컬러 및 기록 횟수, 좁은 탐색 레일은 사용자 검토 중인 예시다. 팀 합의·실 데이터가 없는 부분은 확정 기능처럼 표시하지 않는다.
- 계절 그림은 원본 비율과 본문 가독성을 지키고, 미리보기 경계·가상 기록·로그인 시뮬레이션은 명확히 밝힌다.
