# 잇플 연동 (EatsMine)

EatsMine의 존재 이유는 공모전이 인정하는 **잇플 유입 순사용자**다. 잇플 결과를 잘못 표시하거나 링크를 건드리면 서비스가 동작해도 실적이 0이 되거나 약관 위반이 된다. 그래서 이 스킬의 규칙은 대부분 "편하게 바꾸고 싶은 것을 바꾸지 않기"에 관한 것이다.

## 먼저 확인할 것

1. `docs/plan.md` §6(데이터 연동), §7(AI), §11(API 계약). 구현 판단의 기준이다.
2. `docs/CONTEST.md`, `docs/BLOCKERS.md`(로컬 전용). 대회 약관·권한의 미확인 항목이 여기 있다.
3. 필드나 동작이 불확실하면 원문을 다시 읽는다: 고정본 `bccard-eatpl-search` 스킬(k-skill 커밋 `c41a117`), [API 정의서](https://eatpl.dothome.co.kr/api/), [신청 안내](https://edu.bccard.ai/static/contest/apply.html). 우선순위는 대회 신청 안내·약관 > 승인된 API 정의서 > k-skill(개인 조회용 스킬). 아래 요약은 2026-11-23 `c41a117` 기준이다(feature 가이드는 `46d46d6c` 시점 경로 이력으로 확인, 내용 차이는 확인하지 않음).

## 확인된 데이터 계약

| 항목 | 내용 |
|---|---|
| 입력 | `location`/`address`(주소·지역 텍스트), `merTpbuzNm`/`genre`(업종 대·소분류), `merNm`/`merchant_name`(가맹점명 일부) |
| 결과 수 | 최대 100건, **최근 1개월 BC카드 결제 기반 매출 상위 순** |
| `merUrl` | 잇플 상세 링크(`web.paybooc.ai`). 행마다 응답값 그대로 |
| `allSaleRnk` / `ccgSaleRnk` | 전국 / 지역 매출 상위 **백분위**. 낮을수록 상위. 매출액(원)이 아니다 |
| `srtTime` / `endTime` | 결제 기반 **영업 예상 시간**. 실제 영업시간이 아니다 |
| 좌표 | **TM128**. WGS84 지도 마커에 그대로 쓰면 엉뚱한 위치에 찍힌다. 변환하거나 `kakao-map`으로 지오코딩한다(P0-03) |
| 오류 | 400 = 입력 없음/잘못됨, 401/403 = IP·기관코드·권한, 503 = 기관코드 등 설정 누락, 502 = upstream 연결·응답 오류 또는 `rspCode` 실패·응답 구조 불일치(semantic error) |

원본 계약 전체는 `bccard-eatpl-search` 스킬(k-skill 고정본)의 instruction.md에 있다. 표에 없는 응답 키(가맹점명·주소 등)는 실제 응답이나 그 문서로 확인한 뒤 매핑한다. instruction.md 예시의 `{merNm}`, `{addr}`가 응답 키로 보이지만, 실제 응답 한 건으로 확인하기 전에는 확정하지 않는다. 확인한 출처를 코드 주석에 남긴다.

주소 텍스트 검색이지 반경 검색이 아니다. "내 주변 1km" 같은 표현을 쓰지 않고, 거리가 필요하면 지도 API 좌표로 따로 계산했다고 밝힌다.

## 링크: merUrl은 손대지 않는다

공모전 집계는 등록 도메인에서 사용자 브라우저가 merUrl로 직접 이동해야 잡힌다. 그래서:

- `<a href={item.merUrl} target="_blank" rel="noopener">`처럼 응답값을 그대로 href에 쓴다. 단축 URL, `/go?url=` 같은 자체 리다이렉트, UTM 등 쿼리 추가, 서버 측 302 모두 금지.
- `rel="noreferrer"`는 리퍼러를 지워 집계를 깨뜨릴 수 있다. Referrer-Policy 설정(`next.config`의 headers, `<meta name="referrer">`)도 바꾸기 전에 대회 요건을 확인한다. 기본값을 유지하고, 바꿨다면 브라우저별로 실제 이동을 확인한다.
- URL은 **고치지 않되 검증은 한다**: `new URL(merUrl)`로 파싱해 `https:` + 호스트 정확히 `web.paybooc.ai` + 경로 `/mer/web/profile/<id>`(신청 안내 형식)인지 본다. 하나라도 아니면 그 매장을 결과에서 빼고(가짜 링크·잇플 홈으로 대체 금지), 민감값 없는 진단 로그만 남긴다. 정규화 단계에서 거르고 테스트로 고정한다. 형식이 바뀌었다는 공식 근거가 생기면 기준과 테스트를 함께 고친다.
- 클릭 이벤트(`eatpl_outbound_clicked`, `POST /api/events/outbound`)는 `navigator.sendBeacon`이나 `fetch(..., {keepalive: true})`로 보내고 **결과를 기다리지 않는다**. 기록 실패가 이동을 막으면 안 된다. `preventDefault()` 후 기록하고 `location.href`로 보내는 패턴도 쓰지 않는다.
- 이동 직전 로그인·설문·광고 팝업을 띄우지 않는다(기획서 §2).
- **인앱 브라우저(카카오톡·인스타그램·페이스북·네이버 앱·에브리타임 등)에서는 유입이 유실될 수 있다**(신청 안내). 대응은 아직 팀 미채택 실험이다(`docs/WINNING-STRATEGY.md`). 채택되면 원칙은 하나다: 외부 브라우저로 넘길 대상은 **잇플 URL이 아니라 등록 호스트의 EatsMine 페이지(현재 검색 상태 포함)**이고, 사용자가 거기서 원본 merUrl을 눌러야 한다. 잇플 URL을 바로 외부로 넘기면 등록 도메인 경유 증거가 사라질 수 있다. 외부 열기 스킴은 실제 기기 동작과 대시보드 반영을 확인하기 전에는 기본 동작으로 넣지 않는다.
- 체류 요건이 있으므로 "지금 그 지역에서 먹을 곳을 찾는 사람"이 누르게 만든다. 클릭만 늘리는 문구·자동 이동·반복 클릭 유도는 하지 않는다.

## 표시 문구

- 출처: 결과 근처에 항상 `eat.pl 잇플 · BC카드 결제 데이터 기반`.
- 순위: `전국 매출 상위 0.04%`처럼 백분위를 소수점 보존해 표시. "인기 1위", "평점", "매출 ○○원", "만족도"로 바꾸지 않는다. 별점 아이콘을 붙이지 않는다.
- 시간: `영업 예상 시간 11:00–21:00`. "영업 중", "지금 열림"으로 단정하지 않는다.
- 다른 출처(카카오 평점 등)를 섞으면 출처를 따로 붙이고, 없으면 `미확인`. 추정하지 않는다.
- EatsMine이 BC카드·잇플 공식 서비스로 보이지 않게 한다.

## 서버 구조 (기획서 §9, §11, 실제 저장소 2026-11-24)

- 팀 저장소는 npm workspaces 모노레포다: `apps/web`(Next.js 16, 포트 3000), `apps/api`(NestJS 12 + Drizzle + pg, 포트 4000, `WEB_ORIGIN` CORS). 기획서 §9의 "Next Route Handler BFF" 대신 팀이 NestJS API를 택했다. 잇플 호출은 **`apps/api` 서버에서만** 한다. 웹은 `NEXT_PUBLIC_API_URL`로 우리 API만 부른다.
- 기관코드·키·relay 토큰은 `apps/api` 환경변수로만 읽는다. `apps/web`의 `NEXT_PUBLIC_` 변수에 넣지 않는다. 값은 로그·Git·에러 응답에 넣지 않는다.
- 외부 DTO(fetch, 타임아웃)와 정규화(DTO → 앱 도메인 타입)를 분리한다. NestJS에서는 `apps/api/src/eatpl/`에 client·normalize·service를 두는 식으로 모듈화한다(위치는 팀 구조를 먼저 확인). 화면 컴포넌트는 외부 DTO 필드명을 모른다.
- 팀 공통 UI의 `StarRating`은 사용자 리뷰 전용이다. 잇플 결과 카드(`ItemCard` 등)의 `meta`에 별점을 넣지 않는다. 매출 백분위는 별점이 아니다.
- `/api/restaurants` 응답 형식: 정상 `200 {items:[{id,name,address,category,rankPercentile,merUrl,lat,lng}],source,updatedAt}`, 결과 없음 `200` 빈 배열, 오류는 구조화된 코드. nullable 필드를 타입에 명시.
- 오류를 구분해 화면에 다르게 보여준다: 입력 오류(400), 권한·IP(401/403), 외부 장애(502), 프록시 설정(503), 결과 없음(빈 배열), 좌표 매칭 실패(카드는 보여주되 지도 마커만 생략). 하나의 "오류가 발생했습니다"로 뭉개지 않는다. 사용자 화면에는 상태 코드·엔드포인트·필드명을 쓰지 않고, 무엇을 하면 되는지("지역을 넓혀 다시 찾아보세요")를 쓴다.
- 빈 결과는 주소 텍스트가 너무 좁거나 업종 표기가 명세와 달라서일 수 있다. 자동 재시도 루프를 돌리지 말고 범위를 넓히는 선택지를 사용자에게 준다.

## 데이터 보관 주의

대회 약관(PDF 제9조의2, docs/CONTEST.md)은 데이터를 등록 서비스의 **표시 용도로만** 쓰고 원본을 별도 축적하지 말라고 한다. 메모리·짧은 TTL 캐시가 허용된다는 문구는 없다. "짧으면 축적이 아니다"로 해석하지 않는다. 주최 측 확인 전에는 요청 시점 조회만 쓰고 DB·파일 캐시, 응답 원문 로그, CDN/프레임워크 데이터 캐시(Next `fetch` 캐시, `cacheComponents` 포함)에 응답이 남지 않게 한다. 허용이 확인되면 대상 필드·저장 계층·TTL·삭제 방법을 문서에 적고 적용한다. 사용자 기록(리뷰·방문)은 잇플 데이터와 분리해 저장 허용이 확인된 최소 참조 식별자만 둔다(기획서 §10 `reviews.restaurant_id`→`restaurants` FK는 이 점에서 재검토 필요). 응답 원본을 테스트 fixture로 커밋하지 않는다(가공된 가짜 데이터 사용).

## AI 추천과의 경계 (기획서 §7)

LLM은 질의를 `{region, foodTags, excludes, ...}` 같은 검색 조건으로만 바꾼다. Zod로 검증하고, 실패·타임아웃이면 수동 검색으로 fallback한다. 카드에 나오는 식당·순위·시간·링크는 전부 잇플 응답에서만 온다. LLM이 만든 식당명이나 설명을 잇플 결과처럼 섞지 않는다.

## 권한·테스트·실적

- 제휴 승인·기관코드·IP 등록과 k-skill 프록시의 서비스 이용 허용 범위는 미확인일 수 있다(docs/BLOCKERS.md). 권한 없이 실서비스 연동, 대량·반복 호출, 스크래핑을 하지 않는다.
- 실 데이터가 없을 때는 mock을 쓰되 화면과 코드에 가짜 데이터임을 분명히 한다. mock의 merUrl은 실제 잇플 링크처럼 보이게 만들지 않는다.
- 테스트 클릭과 실제 이용 실적을 구분한다. 자체 클릭 로그와 주최 측 집계 수치를 합산하거나 같은 값처럼 보여주지 않는다.
