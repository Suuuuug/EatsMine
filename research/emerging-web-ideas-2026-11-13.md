# 최근 뜨는 웹 서비스에서 찾은 잇플 아이디어

작성·웹 확인: 2026-11-13 KST. 팀 토론용 가설. 방향은 **데이터·비교·공략·짧은 게임 중심에 가벼운 위트 한 스푼**이다. 특정 성별이 특정 기능을 선호한다는 주장은 하지 않는다. 아래 아이디어의 인기·차별성·사용자 수요는 검증 전이다.

## 먼저 볼 만한 방향

**1순위 가설: 식당 메타 브리핑.** 게임 공략 사이트의 ‘지금 조건에 맞는 선택지와 그 이유’를 식당 결정에 옮긴다. 잇플 검색 응답에서 확인 가능한 항목만 비교하고, 부족한 정보는 빈칸으로 남긴다. 점수보다 근거와 선택 조건을 앞세우는 것이 핵심이다.

**2순위 가설: 오늘의 지역 작전판.** World Monitor의 상황판을 한 동네의 식당 탐색에 응용한다. 필요한 정보가 API에 얼마나 있는지에 따라 성립 여부가 갈린다. **3순위 가설: 한 끼 블라인드 매치.** 두 선택지를 비교하는 Arena의 동작을 가져오되 가게 품질에 대한 근거 없는 순위를 만들지 않는다.

## 트래픽 자료를 읽는 방법

[Similarweb의 국내 순위](https://www.similarweb.com/top-websites/korea-republic-of/)와 [글로벌 상위 100](https://www.similarweb.com/blog/research/market-research/most-visited-websites/)은 존재하지만, 전체 순위는 오래된 검색·동영상·소셜 서비스가 대부분이라 이번 탐색에 적합하지 않다. 대신 [국내 게임 기타 분야 급상승](https://www.similarweb.com/top-websites/korea-republic-of/games/games/trending/), [Digital 100 성장 보고서](https://ir.similarweb.com/news-events/press-releases/detail/140/similarwebs-annual-digital-100-report-finds-serious-utility-powers-the-fastest-growing-websites-and-apps?orderBy=-published_date), 신생 서비스의 공개 지표를 교차 확인했다. 웹 방문량은 추정치이며 순 사용자·앱 사용량·구매·충성도와 다르다. 성장률은 출발점이 작으면 높게 나타날 수 있다. 국내 분야별 순위와 글로벌 방문·이용자 수는 범위와 시점이 달라 서로 순위를 매길 수 없다.

## 아이디어 1. 식당 메타 브리핑 — MetaBot식 공략 화면

**상황:** 대학가나 직장 근처에서 매번 같은 몇 군데만 떠올라, 오늘 조건에 맞는 다른 선택지를 빠르게 좁히고 싶다.

**흐름:** 동네 문자열과 공식 지원 업종 선택 → 잇플 검색 → 반환된 실제 항목을 동일한 기준으로 나란히 비교 → 사용자가 가게를 고르고 잇플 상세 열기. 예를 들어 ‘신촌 + 한식’을 고르면 가게별로 응답에 실제로 있는 명칭·주소·제공 지표를 보여준다. 정렬은 해당 응답 필드의 정의와 비교 가능성이 확인된 경우에만 제공한다.

**화면 한 스푼:** `오늘의 작전: 점심 후보 정찰` / `확인된 정보 2개 · 미확인 정보 3개`. 군더더기 없는 표에 작전명만 가볍게 얹는다. S티어나 승률을 가짜로 만들지 않는다.

**차별 가설:** 긴 후기 대신 ‘무엇을 알고 무엇이 없는지’를 빨리 파악할 수 있다. 실제로 유용한 필드가 적으면 일반 검색과 차이가 사라진다.

**MVP:** 지역·업종 입력, 검색 결과 최대 3개 비교, 필드 설명, 상세 버튼, 빈 결과 재검색. 목업은 가상 데이터. 실 데이터 허용과 필드 계약은 사전 확인. 개인 기록·회원가입 불필요.

## 아이디어 2. 동네 작전판 — World Monitor식 상황 대시보드

**상황:** 낯선 동네에서 장소 이름을 하나씩 검색하기보다 지역 전체의 선택지를 한눈에 보고 싶다.

**흐름:** 사용자가 동네와 업종을 고른다 → 실제 응답의 가게 목록과 제공 지표를 패널로 확인한다 → 항목을 클릭해 가게 상세를 확인한다. 지도는 좌표 제공·지도 사용 권한·비용이 확인된 경우에만 적용하고, 그 전에는 목록과 지역 텍스트로 시연한다.

**화면 한 스푼:** `작전 지역: 성수` / `확인된 후보 8곳`. 비 오는 날 지도 같은 연출은 가능하지만 실제 날씨와 연결하지 않았다면 날씨 정보처럼 보이지 않게 한다.

**실패 조건:** 데이터가 단순 목록뿐이면 대시보드는 장식이 된다. 실시간 혼잡·대기·현재 영업 여부·이동거리·날씨를 만들어 표시하지 않는다. 과거의 혼잡 시간은 현재 혼잡도가 아니다.

**MVP:** 가상 응답으로 목록·정보 패널·필터를 우선 시험. 상세 연결은 권한 확인 후 실제 검색 응답 URL 그대로 사용.

## 아이디어 3. 한 끼 블라인드 매치 — Arena식 1 대 1 비교

**상황:** 후보가 여러 개라 선택이 어렵고, 이름이나 인기에 끌리기 전에 현재 조건에 맞는 후보를 살펴보고 싶다.

**흐름:** 지역·업종 검색 → 비교 가능한 실제 응답 항목이 있는 가게 두 곳 제시 → 처음엔 이름을 가리고 주소 등 확인 가능한 정보만 제시 → 사용자가 A/B 또는 ‘둘 다 모르겠다’ 선택 → 이름 공개 → 두 가게 중 하나의 잇플 상세로 직접 이동. **명칭을 숨겨도 주소 등으로 가게를 알아볼 수 있어 완전한 블라인드는 아님.**

**화면 한 스푼:** `A vs B. 간판 빼고 한 판.` 선택의 이유가 불충분하면 ‘정보 부족’으로 끝낼 수 있다.

**중요한 반론:** 방문하지 않고 고른 것은 선호 투표이지 맛이나 만족도 평가가 아니다. 데이터가 부족하면 블라인드가 의미 없고, 서로 다른 종류의 지표로 우열을 계산하면 오해를 부른다. MVP에 공개 순위·승률·전국 최강 표현은 넣지 않는다. 둘 다 제외·재검색 가능.

**MVP:** 한 기기에서 두 후보 비교, 공개, 상세 이동. 계정·투표 저장·다인 협업 없이 검증.

## 아이디어 4. 오늘의 한 끼 미션 — 짧은 퀴즈에서 실제 검색으로

**상황:** 친구에게 링크를 보내 함께 즐길 만한 짧은 문제를 풀고 나서 실제 식사 후보까지 찾는다.

**흐름:** 운영자가 검증한 자체 일반 퀴즈 1개(예: 음식의 원산지, 정답 출처 명시) → 결과에서 ‘이 업종 찾아보기’ 선택 → 지역 입력 → 잇플 검색 → 실제 가게 상세. 퀴즈가 식당 검색으로 이어지기 싫은 사람은 건너뛸 수 있다.

**화면 한 스푼:** `오늘의 임무: 세 문제 중 두 문제 돌파` / `지식은 만렙, 점심은 아직 미정`. 예시일 뿐 사용자 테스트가 필요하다.

**주의:** 퀴즈 정답을 잇플 가게의 메뉴 판매 여부로 간주하지 않는다. 정답별 판매점 매칭은 API가 지원할 때만. 게임만 하고 이탈하거나 문제 제작이 부담일 수 있다. 제시된 Krillion 사례는 데이터 신뢰가 낮으므로 성공을 보장하는 근거가 아니다.

**MVP:** 출처를 확인한 수동 문제 3개와 선택적 지역·업종 검색. 날짜별 갱신·리더보드·실시간 경쟁 없이 먼저 테스트한다.

## 아이디어 5. 조건 빌더 — Lovable·Base44식 즉시 결과와 수정

**상황:** 이용자가 검색 필터의 이름을 몰라도 ‘학교 근처에서 한식’처럼 요청하고, 잘못 이해한 조건을 바로 고치고 싶다.

**흐름:** 사용자가 문장 또는 수동 선택으로 동네·업종 입력 → `이해한 조건: 신촌 / 한식`을 편집 가능한 칩으로 표시 → 명시적으로 검색 → 잇플 결과 → 상세. 임의 지리 추정 없이 사용자가 실제 검색어를 확인한다.

**화면 한 스푼:** `조건 확인 완료. 후보 탐색을 시작합니다.` 결과가 없다면 `이번 조건으로는 후보를 찾지 못했어요. 동네나 업종을 바꿔보세요.`

**MVP:** 수동 칩 입력과 정해진 규칙만으로 우선 시연. 자유문장 해석용 AI는 가치·개인정보·비용과 대회 요건을 확인해 선택한다. AI는 없는 메뉴·가격·영업시간을 만들어내면 안 된다. 단순 챗봇형 검색에 머물 위험이 있어 사용자에게 실제 시간 절약이 있는지 검증한다.

## 선택을 위한 작은 실험

1. 가상 식당 6개를 같은 내용으로 준비해 ‘일반 목록 / 메타 브리핑 / 블라인드 매치’를 각각 보여준다. 실제 API 데이터나 실제 가게 평가처럼 표시하지 않는다.
2. 목표 사용자가 평소 점심을 정하는 상황을 말한 뒤 한 후보를 고르게 한다. 성공 여부, 걸린 시간, 어느 정보가 결정에 필요했는지와 상세를 열 의향을 관찰한다. 소수 관찰 결과를 전체 이용자 통계로 일반화하지 않는다.
3. 작전판은 사용자가 지도 없이도 선택에 도움을 받는지, 퀴즈는 놀이 후 실제 검색으로 이어지는지를 따로 확인한다. 예상치나 순 사용자 수를 조작하지 않는다.
4. 우선 후보를 정한 뒤 잇플 공식 검색의 지원 필드·표시·보관 권리 및 서비스 운영 권한을 확인한다. API 데이터 원본 축적·제3자 제공 제한은 [대회 요건](../docs/CONTEST.md)을 따른다. 반환된 상세 URL은 변경 없이 등록 도메인의 사용자 브라우저에서 직접 연다. 테스트 클릭은 공식 순 사용자 성과가 아니다.

## 열린 질문
