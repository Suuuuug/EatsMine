# 팀원 아이디어 검토와 선택 논의

작성·확인: 2026-11-13 KST. 팀 논의용 초안이며 주제 확정이나 사용자 검증 결과가 아니다. 이후 팀 방향은 상금보다 포트폴리오를 우선하고 자체 AI 기능을 필수로 가정하지 않는 것으로 명확해졌다. 아래의 우선 검증 추천은 확정이 아니라 재평가할 초기 제안이다. 원본: [구글 문서](https://docs.google.com/document/d/1B3WgInsAMGQc172LDq8xuc2woek3sV4C-ppglgnqIzg/edit)와 [푸드 파이트 기획서](team-ideas/잇플공모전아이디어_태권.docx). 원본의 아이디어와 아래의 검토·제안은 구분한다.

## 먼저 판단할 내용

**추천: ‘같이 한 끼’와 푸드 파이트를 하나의 메뉴 결정 흐름으로 묶어 가장 먼저 가볍게 검증한다.** 위치와 메뉴를 고른 후 조건에 맞는 잇플 후보를 보여 주고, 동점일 때 게임 연출을 선택하는 방식이다. 재미가 유입·결정에 도움이 되는지는 가설이다. 중간지점 플래너는 이동시간 데이터의 권한과 비용 확인 후 별도 후보로 유지하고, 숨은 맛집은 현재 혼잡도와 평점의 신뢰 가능한 제공 근거가 확인되기 전에는 원안 구현을 보류한다. 팀의 결정은 아직 없다.

| 후보 | 사용자가 얻는 가치 / 대회 연결 | 검토 판단과 핵심 불확실성 |
|---|---|---|
| 푸드 파이트 (태권) | 싫은 메뉴를 제외하고 후보를 고른 뒤 게임으로 최종 메뉴 결정; 결과에서 식당 탐색 | 우선 검증. 선택 과정의 재미와 실제 식당 탐색 전환은 가설. 다인 동시 참여와 한 사람이 대신 선택하는 방식은 다름. 10초 강제 연출이 이탈을 줄이는지도 미검증. |
| 같이 한 끼 (기존) | 일행의 취향을 조율하고 식당 결정 | 푸드 파이트의 문제와 겹치므로 함께 비교. 실제 조건 입력과 선택 부담, AI의 효용·비용 확인 필요. |
| 모임 중간지점 플래너 (구글 문서) | 각자의 출발지에 맞는 모임 지역과 식당, 링크 투표 | 매력적인 문제이나 실제 공평한 이동시간 계산·대중교통 데이터, 비용·권한 및 경쟁 차별화가 어려움. 별도 후보로 유지. |

| 회식 조건 정리 / 낯선 동네 한 끼 (기존) | 각각 단체 장소 선정 / 낯선 곳의 빠른 식사 결정 | 보조 비교 후보. 단체 적합성·가격 데이터와 일반 검색 대비 차별성 확인 필요. [기존 검토](ideas.md) 참고. |

## 푸드 파이트: 원안과 조정할 점

**원안:** 인원과 위치 설정 → 메뉴 밴·픽 → 10초 난투 → 우승 메뉴와 잇플 이동. 링크 공유, 메뉴 신청, 사운드·폭죽도 제시했다. 30초, 빠른 로딩, 대량 유입, 무료 운영과 전환은 목표 또는 가설이지 측정된 성과가 아니다.

- **메뉴와 실제 가게 연결:** 잇플 검색은 주소·업종·가게 이름 조건을 지원하지만 모든 우승 메뉴가 업종값으로 검색 가능하거나 음식점의 실제 메뉴를 보장하는 것은 아니다. 지원 분류를 확인하고 검색 결과가 없으면 지역·업종을 다시 선택하도록 한다. 단순히 잇플 홈으로 보내는 것과 검색 API로 실제 가게를 찾아 그 상세 URL로 보내는 것은 대회 흐름상 다르다.
- **선택권과 유입:** 자동 카운트다운 이동 대신 명시적인 식당 상세 버튼을 제안한다. 대회 안내상 반환된 상세 URL을 변형하지 않고 등록 호스트의 사용자 브라우저에서 직접 열어야 한다. 공유·게임 참가자 수가 잇플 순 사용자 수와 같다는 보장은 없고, 유입 조건과 중복 제거는 공식 집계에 따른다.
- **일행의 의사 반영:** 한 화면에서 대표자가 선택하는 MVP와 각자가 링크로 밴·픽을 보내는 협업은 별도다. 후자는 서버·저장·동시성·중복 참여 처리가 필요하다. 먼저 실제 모임에서 대표자 방식의 불편을 관찰한다.
- **게임 공정성:** 후보 선정 후 승자를 무작위로 정하는지, 선택 횟수에 가중치를 두는지 명시한다. 미리 정한 결과를 실력이나 실제 충돌 결과로 오해시키지 않는다. 애니메이션 건너뛰기와 동작 줄이기, 무음 기본값을 검토한다.
- **AI 역할:** 대회 AI 필수 여부는 미확인. 예를 들어 사용자가 입력한 자유 문장에서 메뉴 선호·제외 조건만 정리하는 보조 기능을 시험할 수 있다. 확인되지 않은 가게 메뉴·가격·영업 상태를 생성하지 않으며, AI 없이도 선택할 수 있게 한다. 모델 비용·개인정보 처리는 별도 결정한다.
- **비용과 구현:** 특정 라이브러리·무료 호스팅·소리·모션은 확정 아님. 무료 한도와 서비스 약관을 확인하기 전 리소스를 만들지 않는다. 지리 위치는 선택 사항으로 두고 거절 시 지역 수동 입력을 제공한다.

## 두 구글 문서 후보의 데이터 조건

### 숨은 맛집

[k-skill 원본 지침](https://github.com/NomaDamas/k-skill/blob/main/bccard-eatpl-search/instruction.md)은 최근 1개월 결제에 기반한 매출 순위, 예상 영업시간 및 혼잡 요일/시간을 설명한다. 문서에서 **실시간 현재 혼잡도·대기시간**을 제공한다는 근거는 확인하지 못했다. 과거 혼잡 시간의 반대가 지금 한산함을 보장하지도 않는다. 또한 표본·갱신 주기·결측값의 의미는 확인이 필요하다.

[카카오 Local 공식 응답 명세](https://developers.kakao.com/docs/ko/local/dev-guide)의 장소 검색 필드에는 평점·리뷰 수가 없다. k-skill은 별도 헬퍼로 공개 검색 페이지 평점을 읽는다고 설명하지만, 이는 공식 Local API의 평점 제공을 의미하지 않으며 자동 조회·서비스 재사용 권한과 지속성은 미확인이다. 매장명·주소 매칭이 모호하면 평점을 표시하지 않아야 한다. 학교 주변의 대기 문제는 구체적이므로 인터뷰로 확인하되 실제 데이터 없이 ‘현재 한산’·‘평점 높은 숨은 맛집’을 약속하지 않는다.

개인 맛집 도감은 기기 내 저장으로 가능하지만 기기 간 동기화와 사용자 전체 평점 집계는 별도 서버·저장·동의 및 남용 대응이 필요하다. 브라우저 로컬 저장만으로 집계할 수 없다.

### 모임 중간지점

좌표의 기하학적 중심은 실제 경로·환승·소요시간을 반영하지 않는다. ‘이동시간이 공평하다’고 말하려면 교통수단·시간대와 목적 함수(예: 최장 이동시간 최소화 후 차이 비교), 경로 실패를 정해야 한다. [카카오모빌리티 대중교통 통합 길찾기](https://developers.kakaomobility.com/affiliate/publictransit/multimodal.html)는 소요시간을 설명하지만 [제휴 API 안내](https://developers.kakaomobility.com/affiliate/index)는 해당 제휴 API에 사전 계약이 필요하다고 한다. 일반 자동차 길찾기는 [별도 쿼터](https://developers.kakaomobility.com/price/)가 안내돼 있으며 대중교통의 무료 사용을 뜻하지 않는다. 선택한 경로 API의 계약·가격·쿼터를 실제 이용 전 확인한다.

경로 데이터 없이 시험할 때는 사용자가 직접 합의한 동네를 입력받거나, 좌표 중심을 ‘지도상 참고 지점’으로 표시하고 공평성이나 소요시간을 주장하지 않는다. 지역 문자열 검색은 반경 검색이 아니므로 실제 인근 여부 확인도 별도 과제다. [꿀툴 중간지점](https://kkultools.com/meet)과 [meetmiddle](https://meetmiddle.co.kr/) 등은 유사 기능을 표방하므로, 해당 서비스의 주장만으로 정확도나 이용량을 입증할 수는 없지만 차별화 검토가 필요하다.

## 대회 공통 조건 및 다음 실험

공식 [대회 신청 안내](https://edu.bccard.ai/static/contest/apply.html) 기준 등록 마감은 2026-12-03, 집계 종료는 12-13이다. 등록 완료일부터의 집계, 등록 도메인·상세 링크 조건과 API 운영 권한의 불일치는 [대회 요건](../docs/CONTEST.md)에 기록되어 있다. 이 검토에서 권한이 해결된 것은 아니다. 안내는 바뀔 수 있으므로 신청 전 재확인한다.

1. 팀에서 사용자 상황을 하나 정한다: 예를 들어 학교 점심 모임에서 메뉴 합의가 어려운 2~4명. 수요는 아직 가설이다.
2. 실제 지인 모임에서 종이 또는 가짜 데이터 화면으로 ‘밴·픽만’과 ‘밴·픽+선택적 게임’을 비교한다. 메뉴 선택 완료 여부, 소요 시간, 결과 만족, 식당 상세를 보고 싶었는지와 이유를 관찰한다. 참여자 수·조건을 기록하며 대표성이나 유입 성과로 과장하지 않는다.
3. 잇플 서비스 이용 권한과 검색 분류·응답 계약을 확인한다. 가능하다는 답을 받기 전 실 API 운영이나 대량 호출은 하지 않는다. 카카오 평점·길찾기 선택 시 각 제공자의 재사용 권한과 비용도 확인한다.
4. 팀이 결정할 질문: 게임의 재미와 빠른 결정 중 무엇을 우선할지, 다인 링크 투표가 필수인지, 주 사용자·지역이 어디인지, 팀 인원과 가용 시간·예산은 얼마인지. 실험 결과 및 권한에 따라 후보를 재평가한다.

## 확인 범위와 한계

구글 문서의 두 탭과 추가 DOCX 본문을 읽고 원문 지침·공식 API 문서 및 공개 선행 사례를 2026-11-13 확인했다. 실제 API 호출, 이용 계약, 사용자 인터뷰, 서비스 구현, 집계 검증은 하지 않았다. 경쟁 사례는 자체 기능 설명을 근거로만 비교했다. forge는 이전 Claude 한도 오류로 결과가 없으며 이 문서는 그 산출물이 아니다.
